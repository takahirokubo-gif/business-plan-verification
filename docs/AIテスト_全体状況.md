# AIテスト 全体状況

最終更新：2026-08-07

このプロダクト（事業計画検証Lv1）が、実務で出てくる資料の「複雑性」をどこまで
自動で処理できるかを測るテストの、目的・設計・実施状況・残タスクをまとめる。

---

## 1. 何を測るテストか

融資審査で扱う資料（財務モデルExcel・DDレポートPDF）には、機械処理を妨げる
「複雑性」が必ず含まれる。単位がシートごとにバラバラ、科目名が社内独自、
旧版シートが混ざっている、資料間で数字が食い違う——といった事象である。

このテストは、そうした複雑性を **22項目に類型化**（複雑性マトリクス）し、
1項目ずつ「仕込んだデータ」を作って、プロダクトが期待どおりに振る舞うかを検証する。

### 期待動作は2種類ある

| 期待動作 | 意味 | 該当ID |
|---|---|---|
| **自動処理** | ユーザーに意識させず黙って正しく処理するのが正解 | E-1〜E-6・P-1〜P-2 |
| **検知して照会**／**正シート・正ファイル識別** | 機械が勝手に決めてはならず、人に確認を上げるのが正解 | E-7〜E-11・P-3〜P-6・EP-1〜EP-4 |

**「数値が合っていても、勝手に処理していたら失格」** という基準を置いているのが
このテストの要点である。単に転記精度を測るのではなく、
「決めてよいこと」と「聞くべきこと」の境界を守れるかを見ている。

### 複雑性マトリクス（22項目）

| ID | 複雑性 | A | B | C |
|---|---|:-:|:-:|:-:|
| E-1 | シートが複数に分かれ、複数期分ある | ● | ● | ● |
| E-2 | 月次の試算表が含まれる | ● | ● | ● |
| E-3 | 単位の書き方や場所がシートごとにバラバラ | ● | ● | ● |
| E-4 | 項目名が英語表記になっている（年次FY表記含む） | ● | ● | ● |
| E-5 | 実績・計画の期数が資料によって異なる | ● | ● | ● |
| E-6 | 業界特有の言葉が使われている | ● | ● | ● |
| E-7 | 科目の名前や内訳の分け方が独自 | | ● | ● |
| E-8 | 使わない古いシートやメモ書きが混ざっている | | ● | ● |
| E-9 | 同じ構造のファイルがケース違いで複数ある | | ● | ※ |
| E-10 | 本表とは別にKPIを説明する小さな表が散在している | | ● | ● |

| P-2 | 計画の前提条件があちこちの章に散らばっている | ● | ● | ● |
| P-3 | 入り組んだ表がある（多段・脚注参照） | | ● | ● |

| EP-2 | 資料ごとに単位が違う | | ● | ● |
| EP-3 | 資料間で数字が食い違っており、どちらが正か判断が要る | | ● | ● |

Cでは E-12 に置き換える。

**IDの対応**：リポジトリ内の生成仕様（`claude_code_prompt_テストデータAB作成_v2.md` 3章）では
E-n＝En、P-n＝Dn、EP-n＝Xn の表記を使っている。採点の正本はスプレッドシート側の E-/P-/EP-。

### 採点凡例

| 記号 | 意味 |
|---|---|
| ◎ | 問題なし |
| ○ | 完璧ではないが、生成AIによる読み取りが原因ではない（プロダクトの機能範囲・仕様の問題） |
| △ | 完璧ではなく、原因に生成AIの読み取りが含まれるが、明確な技術的障壁にはなり得ない |
| X | テストが失敗しており、原因に生成AIの読み取りが含まれ、今後技術的障壁になることが想定される |

## 2. テストデータの構成

### データセットの世代

| 世代 | ディレクトリ | 位置づけ |
|---|---|---|
| 第1世代（v2） | `testdata/` | 複雑性の定義と数値骨格を確立した版 |

### A / B / C の役割

| セット | 目的 | 資料構成 |
|---|---|---|
| **A（標準）** | 実務で平均的な水準の複雑性。「ユーザーに意識させず自動で正しく処理できるか」＝自動化性能を測る。デモにも使用 | 財務モデル1冊＋統合版DD 1冊（73ページ） |
| **B（難）** | 「勝手に処理せず人に聞けるか」＝判断の境界を測る。**本丸** | 財務モデル2冊（Base/Sponsor）＋デットスケジュール1冊＋DD4分冊（計80ページ） |
| **C（未着手）** | E-12（プルダウン式ケース切替）を含む次世代 | 未作成 |

**A には B専用項目（E-7〜E-11・P-3〜P-6・EP-1〜EP-4）を一切含めていない。**

- 数値の正本：`testdata/generator/spec12.py`（オートスタッフ中部LBO・Project Gear）

## 5. テスト設計の外で判明した重大論点

テストの点数には表れないが、商用化の可否に直結する2件が検証の過程で判明した。

### 5-1. プロンプトの「下駄」— 本番経路で4箇所

`backend/app/extractors/anthropic_extractor.py` の指示文に、**このデータ固有の
シート名・科目名・業界用語**が書かれている。

| 行 | 記述 | 効いているID |
|---|---|---|
| 524 | 「表記揺れ（**Net Sales / Adj. EBITDA**等）は名寄せし」 | E-7 / EP-1 |
| 526 | 「旧版シート（**PL_old**等）・作業用シート・空シートは抽出対象外とし」 | E-8 |
| 573 | 「各内訳科目（**派遣事業売上・その他営業収入・労務費・その他原価・採用費・本社人件費・その他販管費**など）へ分解する」 | E-6 |
| 575-576 | 「KPIドライバー（**稼働人数・在籍数・稼働率・稼働時間・単価・時給・法定福利費率・採用人数・CPA**等）まで分解する」 | E-6 |

加えて `INQUIRY_SCHEMA` の category に照会すべき事象の類型そのものが列挙されている
（単位不明／名寄せ／参照切れ／資料間矛盾／正シート識別／正ファイル識別／作成時点差）。

**下駄の切り分け**

| 層 | 内容 | 扱い |
|---|---|---|
| L1 汎用 | 3段フォールバック、根拠3点セット必須、照会7類型、単位正規化はシステム責務、資料間矛盾は両論併記 | **資産。残す** |
| L2 LBO商品固有 | 資料スロット構成、標準キー（ev/senior_loan/goodwill/normalized_ebitda）、KPI根＝EBITDA、シナリオ3類型 | 商品スコープとして妥当。仕様に明記する。ただし「Base/Sponsorの2ケース決め打ち」は要解消 |
| L3 この案件固有 | 上表の4箇所 | **除去対象** |

`seed.py` / `mock.py` / `fixtures/` にも社名が入っているが、これらはデモモード専用で
実AIの経路には関与しない（`anthropic_extractor.py` に fixtures への参照はゼロ）。

**下駄なしで◎を取った項目**（プロンプトに「月次」「単価改定」「採用チャネル」「寮」
「ティーザー」等の語は一切含まれない）：
E-1・E-3・E-4・E-5・E-9・**E-10**・P-2・P-5・**P-6**。

したがって銀行向けの報告では、
「**指示があれば確実に実行できる**（出荷可能な能力）」と
「**指示がなくても自分で気づく**（未知案件への一般化能力）」を分けて書く必要がある。

### 5-2. ダイジェストの窓（80行 × 30列）— プロンプトでは解決できない

`_excel_digest` は Excel を **80行・30列で無警告に打ち切って**テキスト化している。
B_hard の最大シートは34行×18列だったため、今回のテストでは**一度も窓に当たっていない**。

`actual_data_sample/財務モデルサンプル/` の実物テンプレートの実測：

| ファイル | シート | サイズ |
|---|---|---|
| Company-A-LBO-model-template | LBO | **363行** × 21列 |
| Company A - merger model | CompanyA / CompanyB | **281行** × 13列 |
| Company A - cash sweep model | debt | **203行** × 12列 |
| Company A - DCF / operating model | debt | **136行** × 11列 |
| Company A - operating model | inp | **89行** × 11列 |
| 財務モデルのサンプル | 財務モデル | **82行** × 19列 |

**実物のLBOモデルはほぼ全部が窓の外に出る。**しかも切り落としは無警告なので、
画面上で「AIが見落とした」と「システムが渡していなかった」が区別できない。
解析ログはトークン数と停止理由は出すが、ダイジェストの切り落としは出さない。

| # | タスク | 目的 | 規模 |
|---|---|---|---|
| **1** | L3の4箇所を汎用化 → **データB再実行** | 下駄の実寸を測る。落ちた項目が商用開発での改善対象 | プロンプト修正1時間＋実行10分 |
| **2** | ダイジェストの窓を撤廃＋切り落としの可視化 | 実物モデル（363行）対応の前提条件。プロンプトでは解決不能 | 実装 |
| **3** | **別業種での素通し**（`dummy_input_v2/` のルミエールボーテ：モデル2冊＋DD4分冊） | 業界用語列挙の下駄を外した一般化能力の測定 | 実行のみ |
| **4** | **データAの再テスト** | 改修（3段フォールバック・正常収益力EBITDAの探索指示）でE-2・E-5・P-1が◎になるかの確認 | 実行のみ |
| **5** | `propose_kpi_tree` の種別なしExcel対応 | 3-4の欠陥修正 | 小 |
| **6** | **銀行向け能力ラダー表**（転記／推論／判断の3段階） | A・B揃った結果を営業資料に落とす。3段フォールバックの画面可視化がそのまま素材になる | ドキュメント |
| **7** | **テストデータC の作成** | E-12（プルダウン式ケース切替）と、L2の「2ケース決め打ち」解消の検証 | 大 |

### 判断が必要な点

- **データA再テストのエンジン**：Bと揃えて claude-opus-5 にするか、改修効果だけを見るため前回と同条件にするか
- **EP-4 の期待動作**：マトリクス定義は「軽微な差として扱えるか」（＝整合扱いが正解）だが、`planted_items` の期待動作欄は「検知して照会」。基準が二重になっている

## 7. 実行手順（再現方法）

```bash
# 1. サーバ起動（EXTRACTOR_MODE=anthropic・backend/.env に ANTHROPIC_API_KEY が必要）
cd backend && .venv/bin/python -m uvicorn app.main:app --port 8011
```

```bash
# 2. テスト実行（A または B）
backend/.venv/bin/python testdata_realistic/ai_test/run_ai_test.py B
```

```bash
# 3. 採点
backend/.venv/bin/python testdata_realistic/ai_test/score.py B
backend/.venv/bin/python testdata_realistic/ai_test/match_b.py
```

ランナーは解析を items → kpi → scenarios の3リクエストに分けて呼び、途中のステップが
失敗しても止めずに続行して、HTTPステータス・本文とサーバ側の解析ログ（`analysis_runs`）を
結果JSONに残す。「AIが検知しなかった」のか「打ち切り／エラーで落ちた」のかを
採点時に切り分けるため。

画面から実施する場合は、資料7件をアップロード → 案件情報を読み取り → 登録 → 解析実行 →
「解析ログ」で打ち切り・エラーを確認 → 「確認事項」で照会内容を確認、の順。
